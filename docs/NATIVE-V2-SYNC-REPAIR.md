# 原生 v2 反向同步修复（2026-10-25，v7）

用户验收发现：ZCode 重启后才能看到 Codex 的更新；ZCode 发出的内容在 Codex
重启后仍不出现。本轮允许窗口刷新降级，重点修复反向消息没有被原生读档接受。

## 实际原因

1. 已启用测试会话的同步进程正常运行，但一直处于 `waiting_codex_projection`。
   Codex 分页水位仍是旧文件中的字节位置和编号，与当前原生文件不符。
   排队的六个 ZCode 内容块中，实际可见内容只有一条用户消息和对应回答；
   另外四个是隐藏运行时或步骤信息。
2. v6 补齐索引后，两条可见消息已写入原生文件，等待数清零。然而独立 Codex
   原生恢复仍看不到它们：原会话使用 `multi_agent_version: v2`，旧格式的
   `user_message`/`agent_message` 和手工生成的索引无法构成 v2 原生回合。
   因此文件写入和 SQLite 检查都通过，也不能称为客户端接收成功。

## 修复

- 从当前已校验文件的原生任务/条目完成事件恢复索引，使用来源真实 ID，
  不根据文本或旧字节偏移猜测身份。保留已有原生消息、工具和中断轮次。
- 新的 v2 文本同步使用明确的原生回合开始、条目完成和回合完成记录；
  文件与索引使用相同的稳定 ID，并携带同步来源标记。
- 已经按旧格式投递的文本只补原生展示事件，不改写原历史，不重复模型
  `response_item`，也不提交提示或启动另一端模型。
- 隐藏运行时、推理和步骤信息在确认过滤后从等待队列移除，不计为可见投递。
- 保留源文件身份、摘要、完整行、目标空闲与失败重试保护。缺少完成事件
  或遇到尚未投影且不支持的新原生条目类型时，继续等待或明确报错。

## 已执行验证

**140 项测试通过**，覆盖索引偏移失效、原生 ID、隐藏消息过滤、未知类型保护、
新 v2 编码、旧格式补齐、仅展示事件修复以及中断后不重复投递。

额外使用本机安装的 Codex **0.164.0-alpha.11.1**，在完全隔离的资料目录启动
独立原生服务。保留完整原生表结构及迁移记录，只复制选定测试会话的数据。
通过真正的 `thread/resume` 返回的可见消息条目检查，而非在原文件中搜索字串：

| 验证 | 结果 |
| --- | --- |
| v6 旧格式恢复 | 未读到外来文本，证明仅写文件/索引不足 |
| 旧投递补原生展示事件后恢复 | 用户消息与对应回答各出现一次 |
| 新 v2 编码的隔离后续消息 | 用户标记与回答标记各出现一次 |
| v7 更新后复制实际目标、直接恢复，不在副本额外修补 | 用户消息与对应回答各出现一次 |

验证没有调用 `turn/start`，没有启动模型生成；测试 CLI 未打开生产资料目录。
实际同步仅沿用用户已经启用的测试会话对，保留了原绑定，没有新建或启用
其他会话。同步服务更新前备份选定原生文件、历史索引和投递日志。

执行证据位于 Hub 数据目录 `validation/sync-v6-stage.json`、
`sync-v7-cold-reader*.json`、`sync-v7-deployment.json` 与对应备份目录。
其中包含私人来源标识，不纳入源码仓库。

## 刷新与剩余边界

运行中客户端可能保留会话内存缓存。切换会话可以尝试，但本轮不承诺它会
强制重新读档；重启客户端仍是允许的降级方式。没有修改两款客户端本身，
没有声称实现实时同屏或活跃模型在生成中自动更新上下文。

独立冷启动原生恢复已经通过；桌面窗口实际绘制和模型下一轮理解仍应独立
验收。原生文件权威路径切换、历史回退和并发分支合并不在本轮自动修复范围。
