# 原生客户端刷新桥接（v9，实验功能）

## v9：多轮写入修复

实机发现 v8 在客户端已加载会话时向文件追加记录，会与原生写入器缓存的序号
冲突。首轮可见、下一轮停止，正是这条路径的后果。v9 默认禁止向运行中的分页
Codex 历史文件外部追加。ZCode 新记录先进入持久 outbox，再通过**同一个客户端
后台连接**的 `thread/inject_items` 交给原生写入器编号，不发起模型请求。
界面消息使用独立的带来源记录覆盖层，在恢复会话、分页和刷新事件中提供相同
ID 的已写入条目。原生消息 ID 和持久回执共同防止重试时重复写入。

`native_sync_runtime_writer=false` 仅保留给离线兼容性测试，不应配置给运行中的客户端。
原生接口回执说明记录已写入原生历史；模型是否实际利用内容仍需目标端询问验收。

启动器原生 EXE 的 stdin/stdout 现在按每次读写立即 flush；新增了完整的
EXE → Node → 安装版原生后台测试。小握手消息不再滞留在缓冲区。
隔离原生后台连续三轮与原生自身写入交替测试通过，记录序号连续，冷启动后
三个条目各一次，未调用模型。此前仅测试 Node 入口，没有覆盖完整启动链路。

已产生的历史冲突在 **Codex 客户端及后台退出之后** 由启动器预检修复：
完整备份后，只移除有配对标记且能在 ZCode 找到来源的冲突桥接记录；
原生记录的字节、顺序和序号不改。对应消息回到 outbox 由原生接口补入。
原始文件未变化、原生后台已退出、来源仍存在，三项都成立才写入。
中断通过持久计划恢复；无法证明安全时暂停启动，不猜测重编号。
不会退出正在工作的客户端来执行修复。

以下 v8 的外部追加及只读刷新描述保留为旧路径背景；当前默认采用上述原生写入方式。

历史文件写入、后台可读、窗口显示、下一轮模型读到，是四个不同的验收层次。
v8 为用户明确开启同步的配对增加客户端连接上的刷新事件，不自动建立配对或开启同步。

## 接入方式

启动器使用当前客户端已有的覆盖入口：Codex 的 `CODEX_CLI_PATH`，ZCode 的
`ZCODE_AGENT_SERVER_COMMAND` / `ZCODE_AGENT_SERVER_ARGS_JSON`。
这些变量只传给本次启动的进程。原版程序、用户全局环境变量不改。
先退出客户端，再通过 `D:\ContextHub\启动 Codex 同步桥.cmd` 和
`D:\ContextHub\启动 ZCode 同步桥.cmd` 启动。已有进程不会吸收新的环境设置。
直接用原来的图标启动则没有这条刷新连接，历史文件同步仍独立工作。
客户端升级后路径可能变化，需重新生成启动器。

`runtime/install_bridge.py` 接受显式安装路径，生成原生 EXE 入口和两个启动文件。
需 Node.js、Windows .NET Framework C# 编译器；不会退出或启动客户端。
恢复原图标启动即停止使用桥接。同步配对仍需单独暂停。

## 数据路径

同步服务持久写入完成后，在 SQLite `live_refresh` 表中记录条目 ID。
桥接仅接受本机随机端口、随机令牌、匹配原生目录且仍启用的配对。
令牌不写进报告或聊天。描述符心跳过期不再使用。

桥接转发客户端与其原有后台之间的标准输入输出。补充请求仅用于读取历史；
不发送用户消息，不启动、引导或调用模型，不通过另开的独立后台冒充当前客户端。
当前会话正在生成时等待结束；刷新批次期间，同会话的新提交暂存后顺序转发。

Codex 先用 `thread/turns/list` 获取完整条目。当分页结果滞后时，改用
`thread/read(includeTurns=true)` 读取新持久化的原生条目；只对指定 ID 补发
`item/completed` 和 `turn/completed`，不伪造 `turn/started`。
ZCode 用同一个后台的 `session/resume` 读取快照，转发精确的原生 part DTO。
事件使用 `desktop-continuous` 的未编号模式（`seq=0`），由客户端原生逻辑排序，
稳定 eventId 去重。不会把运行时提醒、元数据 JSON 当作用户消息补发。

## 已验证与待验收

- Python 回归测试覆盖队列持久性、配对暂停、无桥接时等待、鉴权、Origin 拒绝、
  忙碌等待、重复请求去重、分页滞后回退、后台响应不泄漏给客户端。
- 本机安装版 Codex、ZCode 已在隔离原生目录中验证：同一后台运行时，外部写入后
  能读取新增条目，经桥接各收到一次对应更新事件，文字保持一致，未调用模型。
- **真实桌面窗口是否立即渲染新消息仍待验收**。特别是 ZCode 新 message 的角色/布局，
  不能仅凭 `part.upserted` 事件到达宣称完成。
- **下一轮模型实际读取外部消息仍未验证**。不调用 `thread/inject_items` 来冒充界面刷新；
  该接口只补模型历史，且对当前分页记录格式可能产生额外影响。

`notifications_sent` 仅表示事件已发送到客户端连接，不代表窗口已经显示。
没有启动桥接时显示 `waiting_runtime_activation`；未打开配对会话时显示
`waiting_session_open`；生成中显示 `waiting_idle`；读取未就绪时保留待重试。

## 人工验收

首次通过两个启动器启动后，在两端打开已有配对（不要重新导入副本）。
先在 Codex 发一个唯一口令并等本轮结束，观察 ZCode 在不切换会话时是否出现；
再反向发送另一口令。记录源端完成时间、目标出现时间、有无重复及角色错位。
源端尚在生成时等待完成属于当前设计，尚未实现逐 token 同传。
如需验证下一轮模型读取，在目标端单独询问刚才的唯一口令。
界面不刷新时保留现场，查看队列状态，以区分未接桥接、后台未读到、客户端未渲染。
